#### A6 · (schedule item 7) 🔴 THE DATABASE-FIREWALL WORKFLOWS RACE EACH OTHER
**This is the highest-value fix in Part A** because it corrupts the evidence of
every other task. Six workflows share a copied firewall block that reads the
allow-list, appends the runner IP, and **on teardown restores the snapshot it
read at the start** — so two overlapping runs mean the first to finish deletes
the second's entry, and the second fails with
`SSL connection has been closed unexpectedly`, **which is a lie about the cause.**
At least six failed runs on 08-14 came from this and every one looked like a
database outage.

Affected: `backup-production-db.yml` · `apply-migrations.yml` ·
`seed-uat-population.yml` · `seed-sample-population.yml` ·
`seed-repair-journeys.yml` · `diagnose-directory-drift.yml`.

**A retry is NOT the fix** — five retries failed identically on 08-14 because the
entry stays deleted.

🔴 **MY PROPOSED FIX WAS WRONG, AND THE RACE IS EARLIER THAN I SAID.** I wrote
that *"teardown removes only THIS runner's entry … makes concurrency safe by
construction."* Codex refuted it; the Supervisor then read
`.github/workflows/apply-migrations.yml:196-215` and found it is worse:

- **The kill happens at CAPTURE, not at teardown.** The capture step builds its
  snapshot by *filtering out every entry whose description contains
  `ephemeral:`* — deliberately, so a crashed run is self-healing. But that
  filter cannot tell a **dead** run's entry from a **live** one's. Run B's
  capture therefore deletes run A's entry the moment B starts, while A is still
  connected. A's failure follows immediately, and it reads as a TLS error.
- **Render's API takes the WHOLE list.** Both the add (`PATCH` with `merged`)
  and the restore `PATCH` send the entire `ipAllowList`. So *any* variant of
  "remove only my entry" is still a read-modify-write of the whole list against
  a shared resource — **still racy, just less often.** That is precisely the
  kind of "safe by construction" claim this repository has a rule about.

**Corrected fix, in order:**
1. **A shared `concurrency:` group across all six workflows**, so they queue.
   This is the only option that actually removes the race, because the API has
   no atomic per-entry operation. My original note dismissed it as "serialises
   unrelated work" — that cost is real and it is the right price.
2. Give each entry a description carrying the **run id**, and make capture
   preserve foreign ephemeral entries while dropping only entries older than a
   sane TTL. This keeps the self-healing property without the fratricide.

⚠️ `apply-migrations` is auto-triggered by `workflow_run` on every push, so a
manual dispatch made near a push is *guaranteed* to overlap.

**19a · DO NOT CREATE `fleet.vehicles`. The vehicle aggregate already exists.**

⚠️ **Towing is NOT the counter-example — it is the proof.** `towing.recovery_vehicles`

recovered. Towing already does the right thing; I misread it.

**The real decision, which must be made before any SQL is written:**
`core.vehicles.customer_id` is **NOT NULL** and references `core.customers`. So a
fleet's vehicles must be one of:
1. `core.vehicles` whose fleet ownership is expressed through a `core.customers`

2. a fleet-specific extension keyed **one-to-one** to `core.vehicles`; or
3. a distinct aggregate with an explicit identity/synchronisation rule.
**Option 3 is the one that looks easiest and is almost certainly wrong.**

**19b · 🔴 THE CROSS-TENANT BOUNDARY IS NOT IN MY PLAN AND IT IS THE HARD PART.**
`076_fleet_registration_race.sql:140` gives a fleet its **own tenant and
organisation**. A fleet requesting service from an independent workshop is
therefore a **cross-tenant** act, and `(x, tenant_id, organization_id)` FKs
*cannot express it* — that key shape can only point at a parent in the SAME
tenant and organisation. A fleet service request needs a designed contract:
source fleet tenant/org + vehicle identity · destination workshop tenant/org ·
**immutable request snapshots where direct FKs are prohibited** · acceptance and
provisioning in the workshop · disclosure boundaries · lifecycle and audit if
either party is suspended. **This is a core data-model design task, not a detail
inherited from towing.**

**19c · The key rule has THREE tiers, not one.** My draft over-generalised:

| Parent | Key shape |
|---|---|
