## Codex, verbatim

No Critical findings. I found three High and three Medium issues.

### High

- [infrastructure/migrations/086_insurance_enquiries.sql:197](C:/Users/USER/Documents/autoworkshop-ai/infrastructure/migrations/086_insurance_enquiries.sql:197), [line 215](C:/Users/USER/Documents/autoworkshop-ai/infrastructure/migrations/086_insurance_enquiries.sql:215) — The relational INSERT policy validates only `product_id`, `tenant_id`, and `organization_id`. Because `autoworkshop_app` also receives direct `INSERT`, it can supply an arbitrary `product_name`, `premium`, `currency`, `enquirer_user_id`, and contact data for an otherwise valid published product. This contradicts the claims at lines 39–46 and 209–213 that the policy prevents a caller choosing the premium and that these values are necessarily derived. The HTTP endpoint happens to use the safe function, but the database capability does not enforce that path. Minimal fix: do not grant table INSERT to `autoworkshop_app`; grant only `EXECUTE` on `submit_enquiry()`. The definer owner can perform the insert, with FORCE RLS still adjudicating it in production. Adjust verification to test the policy through a dedicated non-login/test role if direct policy testing remains necessary.

- [infrastructure/migrations/086_insurance_enquiries.sql:183](C:/Users/USER/Documents/autoworkshop-ai/infrastructure/migrations/086_insurance_enquiries.sql:183), [line 215](C:/Users/USER/Documents/autoworkshop-ai/infrastructure/migrations/086_insurance_enquiries.sql:215) — The database does not implement the service’s “status is the only thing this may change” rule. The table-wide UPDATE grant and row-only `WITH CHECK` allow the owning insurer to rewrite the shopper’s name, email, message, advertised premium, product, and `enquirer_user_id`, provided the resulting row remains in its organization. The claim in [insurance.service.ts:522](C:/Users/USER/Documents/autoworkshop-ai/apps/api/src/insurance/insurance.service.ts:522) is therefore only true of that one SQL statement, not of the granted capability. Minimal fix: replace table-wide UPDATE with column grants such as `GRANT UPDATE (status, updated_by)`, leaving `updated_at` trigger-owned. If PostgreSQL privilege behavior requires it, grant SELECT separately for `RETURNING`.

- [infrastructure/migrations/verify/086_insurance_enquiries.sql:189](C:/Users/USER/Documents/autoworkshop-ai/infrastructure/migrations/verify/086_insurance_enquiries.sql:189) — Check 4 can pass for the wrong reason. It changes both tenant and organization, then accepts either an RLS error or `foreign_key_violation`. The composite product/organization foreign key rejects that row even if `enquiries_public_insert` is `WITH CHECK (true)`, so this does not prove the policy adjudicates the relationship as claimed. The textual regex check at lines 79–87 is not an adequate substitute. Minimal fix: forge only the tenant while retaining product A’s valid organization and product ID. The foreign key then passes and only the relational policy can reject the row. Add a same-product/same-owner insert with a forged premium if direct INSERT remains granted.

### Medium

- [apps/api/src/insurance/insurance-enquiries.integration.spec.ts:113](C:/Users/USER/Documents/autoworkshop-ai/apps/api/src/insurance/insurance-enquiries.integration.spec.ts:113) — The comment says the anonymous call runs “as the APP ROLE” and therefore exercises the production RLS path. It does not locally: invoking a `SECURITY DEFINER` function switches to the superuser owner, which bypasses RLS despite `SET LOCAL ROLE autoworkshop_app`. The file itself acknowledges that fact elsewhere, making this a direct false claim. It consequently cannot catch the Render-only failure it says it catches. Minimal fix: describe this test as API/service-path coverage only, and add a CI verification environment where the function owner is non-superuser and FORCE RLS genuinely binds it.

- [apps/api/src/insurance/insurance-enquiries.integration.spec.ts:240](C:/Users/USER/Documents/autoworkshop-ai/apps/api/src/insurance/insurance-enquiries.integration.spec.ts:240) — A completely unreachable database skips the sentinel test, and the remaining `dbIt` tests are also skipped. The suite can therefore be green with zero database assertions, despite the comment saying it “says exactly why not.” Minimal fix: fail the sentinel when this integration suite is explicitly selected in CI, or gate skipping behind an explicit opt-out environment variable and report that condition as a failure in the required verification job.

- [packages/marketplace-ui/src/enquiry-form.tsx:87](C:/Users/USER/Documents/autoworkshop-ai/packages/marketplace-ui/src/enquiry-form.tsx:87) — The double-submit protection does not cover the race described by its own comment. Two submit events before React rerenders both close over `busy === false`, so both POSTs proceed. Disabling the button only helps after the render commits. Minimal fix: use a synchronous `useRef` lock set before awaiting the request and cleared on failure, in addition to the state used for rendering.

One additional behavior is explicitly acknowledged but still incorrect: [apps/web/app/cover/[id]/page.tsx:55](C:/Users/USER/Documents/autoworkshop-ai/apps/web/app/cover/[id]/page.tsx:55) maps API/network failure to a 404. A live product therefore appears nonexistent during an outage. Minimal fix: preserve a structured `notFound` versus `unavailable` reason from `fetchInsuranceProduct`, call `notFound()` only for the former, and render a retryable error state for the latter.

Verified as sound: the public POST body exposes no tenant, organization, insurer, premium, or enquiry ID; unpublished and unverified products are filtered in both the definer lookup and policy; anonymous enquiry SELECT is not opened; and the insurer read path is organization-scoped under RLS.
